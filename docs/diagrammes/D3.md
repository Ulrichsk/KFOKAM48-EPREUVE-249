# D3 — Séquence « marquer sa présence »

**Version** : 1.0 (étape 1) · **Source** : `api/contrat.yaml`, `CLIENT.md` §3, EF2/EF3/EF13

Trois scénarios sont détaillés : le **cas nominal** (`201`), le **code expiré**
(`410 CODE_EXPIRE`) et le cas **déjà présent** (`409 DEJA_PRESENT`). Les trois se
déroulent sur l'opération imposée `POST /api/presences { code, etudiantId }`.

Conventions : `PresenceController` ne fait que valider l'entrée et déléguer ; aucune
requête base n'y figure (ENF3). `Gestionnaire d'erreurs` désigne l'unique
`@RestControllerAdvice` qui produit le format `{ "code", "message" }` (ENF4) sans jamais
exposer de stack trace.

## 1. Cas nominal — présence marquée

```mermaid
sequenceDiagram
    autonumber
    actor E as Étudiant
    participant C as PresenceController
    participant S as PresenceService
    participant R as PresenceRepository
    participant DB as Base de données

    E->>C: POST /api/presences { code, etudiantId }
    C->>C: validation du DTO (@Valid)
    C->>S: marquerPresence(code, etudiantId)

    S->>R: composer la recherche du code
    R->>DB: SELECT * FROM sessions WHERE code = ?
    DB-->>R: session trouvée
    R-->>S: session

    S->>S: RG21 session non clôturée ?
    S->>S: RG2/RG3 code non expiré (now <= expiration_at) ?
    S->>S: RG5 étudiant non bloqué (bloque_jusqu_a < now) ?
    S->>S: RG19 étudiant appartient à la promotion de la session ?

    S->>R: existsBySessionIdAndEtudiantId(sessionId, etudiantId)
    R->>DB: SELECT EXISTS (...)
    DB-->>R: false
    R-->>S: false

    S->>R: save(presence, source = ETUDIANT)
    R->>DB: INSERT INTO presences (...)
    DB-->>R: ligne créée (UNIQUE session_id + etudiant_id respectée)
    R-->>S: presence

    S->>R: remise à zéro du compteur de tentatives
    S-->>C: PresenceResponse { id, sessionId, etudiantId, source }

    C-->>E: 201 { "id": 42, "sessionId": 7, "etudiantId": 3, "source": "ETUDIANT" }
```

## 2. Code expiré — `410 CODE_EXPIRE`

```mermaid
sequenceDiagram
    autonumber
    actor E as Étudiant
    participant C as PresenceController
    participant S as PresenceService
    participant R as PresenceRepository
    participant H as Gestionnaire d'erreurs
    participant DB as Base de données

    E->>C: POST /api/presences { code, etudiantId }
    C->>S: marquerPresence(code, etudiantId)

    S->>R: findByCode(code)
    R->>DB: SELECT * FROM sessions WHERE code = ?
    DB-->>R: session trouvée
    R-->>S: session

    S->>S: now > expiration_at (Q2, RG2)
    S->>S: incrémenter le compteur d'échecs (RG5)
    S-->>C: CodeExpireException

    C->>H: propagation de l'exception
    H->>H: mapping CODE_EXPIRE vers HTTP 410
    H-->>E: 410 { "code": "CODE_EXPIRE", "message": "Le code de présence a expiré." }
```

## 3. Déjà présent — `409 DEJA_PRESENT`

```mermaid
sequenceDiagram
    autonumber
    actor E as Étudiant
    participant C as PresenceController
    participant S as PresenceService
    participant R as PresenceRepository
    participant H as Gestionnaire d'erreurs
    participant DB as Base de données

    E->>C: POST /api/presences { code, etudiantId }
    C->>S: marquerPresence(code, etudiantId)

    S->>R: findByCode(code)
    R->>DB: SELECT * FROM sessions WHERE code = ?
    DB-->>R: session trouvée (valide, non expirée)
    R-->>S: session

    S->>R: existsBySessionIdAndEtudiantId(sessionId, etudiantId)
    R->>DB: SELECT EXISTS (...)
    DB-->>R: true (la contrainte UNIQUE a déjà cette ligne)
    R-->>S: true

    S-->>C: DejaPresentException (aucune écriture)

    C->>H: propagation de l'exception
    H->>H: mapping DEJA_PRESENT vers HTTP 409
    H-->>E: 409 { "code": "DEJA_PRESENT", "message": "Cet étudiant a déjà marqué sa présence." }
```

## 4. Points de vigilance démontrés par le diagramme

| Point | Démonstration |
|---|---|
| Aucune requête base dans le contrôleur | Les appels `findByCode` / `existsBySessionIdAndEtudiantId` sont émis par `PresenceService` via `PresenceRepository` (ENF3) |
| Unicité garantie par la base | L'insertion nominale s'appuie sur la contrainte `UNIQUE (session_id, etudiant_id)`, pas seulement sur le test `exists` : un double clic concurrent ne peut pas créer deux présences (RG4) |
| Erreurs normalisées | Les trois cas sortent par le même `@RestControllerAdvice`, avec le format imposé et **aucune stack trace** (ENF4) |
| Ordre de priorité des règles | La session est chargée d'abord, puis les règles sont évaluées dans l'ordre RG21 → RG2/RG3 → RG5 → RG19 → RG4, ce qui garantit qu'un code expiré répond `410` et non `409`, conformément au contrat |
| Préparation de Q4 | Le scénario « code expiré » incrémente le compteur qui déclenche le `429 TROP_DE_TENTATIVES` au cinquième échec (RG5) |
